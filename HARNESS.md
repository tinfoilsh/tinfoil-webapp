# Webapp harness integration

All chat routes use the existing chat UI and `src/services/harness/`. `/harness` is an alias for the main page. The harness origin defaults to `https://chat-api.tinfoil.sh`; set `NEXT_PUBLIC_HARNESS_ENCLAVE_URL` to use another deployed harness's HTTPS origin. `HarnessClient` uses the Tinfoil SDK to verify `tinfoilsh/confidential-tinfoil-harness` for JSON, multipart uploads, binary downloads, and SSE. There is no direct model or sync connection and no development attestation bypass. Besides the harness, the only enclave the browser calls is the summarizer, which summarizes a reply's reasoning while it streams, through its own SDK client as on main.

The browser owns rendering, navigation, microphone recording, passkey ceremonies, anonymous credential acquisition, custody of the content encryption key, and the chats it keeps on the device. The harness owns prompts, model routing, tools, the turn queue, token budgeting, projects, memory, search, sharing, archive conversion, and the transcripts and settings of synced chats. Built-in prompt text comes from the session catalog for viewing and copying in the prompt library.

Anonymous clients call `GET /api/keys/chat` at `NEXT_PUBLIC_API_BASE_URL` directly, so controlplane sees the client IP. The issued `free_` key is cached only in memory and sent as the bearer credential through the harness's attested transport. Concurrent requests share issuance, expiry or HTTP 401 refreshes the key, and account changes abort pending issuance and clear the cache. The browser uses quota metadata for display; the harness validates the key through the existing `/api/shim/validate-key` endpoint before starting work, and downstream services continue enforcing quotas. No identity-forwarding secret or controlplane code change is needed. Signed-in clients continue sending their Clerk JWT.

Anonymous temporary state belongs to the issued key. Reconnects with the same key survive IP changes; a rotated daily key starts a separate scope. The deployed harness must run on a host accepted by controlplane's existing key-validation IP check. A local webapp can use that deployed harness.

The existing message renderers, widgets, sidebars, project panels, settings, and key recovery dialogs remain. Tool results and project/context usage are server data. Imports to the cloud upload the original file; the progress control checks the returned job id. Image galleries download full-size images through the harness, naming the chat (`threadId`) so stored attachments resolve. A stored document's message carries no text, so opening the document or the share dialog reads it on demand through `/v1/attachments/get`, which returns the extracted text; a local chat reads it from the document's stored descriptor, and a shared chat through `/v1/attachments/get-public`. Read aloud, when the session offers `speech`, asks the harness's `/v1/speech` for each chunk of at most 600 characters (two at a time) and plays the 24 kHz PCM it streams back through the same attested client. Account management, billing, public map tokens, safeguard flags (`/api/users/me/safeguard-flags`, polled every 30 seconds while visible), and legacy opaque passkey credential lookup retain their controlplane requests. The harness gives the safeguards each chat's id as its conversation id, so a flag marks that chat read-only by id, for stored and local chats alike.

Storage follows the device's cloud sync setting, as on main. With cloud sync on, the harness stores chats and settings. Without it (the default for a new account), and for signed-out visitors, chats are local threads: the browser keeps them in the `tinfoil-chat` IndexedDB, or in session storage for the tab when signed out (an image's bytes stay in the page's memory and only its thumbnail is stored, so after a reload the chat keeps only the thumbnail), and keeps settings under `tinfoil-user-prefs-local-profile` in local storage (imported once from the previous client's per-setting keys). Each local turn sends `local: true` with the thread's transcript and the settings a prompt reads, never the content key, and the browser merges the run's messages, per-reply metadata, and title back into its copy; image bytes travel only with the last few image messages. Chats the previous client stored there open through a port of the harness's `legacy.go`. With cloud sync on, Enable local chats adds a Local tab for such chats. Projects, favorites, and server search need cloud sync. A signed-in user shares a local chat from its transcript without image bytes (`local: true` on `/v1/threads/share`, when the session offers `localShare`); shares of either kind are keyed by the chat, so the share dialog reads their status and revokes them by chat id. Session storage also holds run routing hints and UI preferences; keys and passkey recovery state remain in local storage. Signout and account changes clear the chat database, local chats included.

When the session offers `transfer`, dragging a chat between the Cloud and Local tabs, or a chat's Move to cloud and Move to local actions, moves it under the same id, as on main: a move to the device stores the transcript `/v1/threads/transcript` returns, with every attachment's content inline, as a local chat and then deletes the cloud copy, removing the local copy again if the harness refuses that deletion (one whose outcome is unknown, as over a dropped connection, keeps it); a move to the cloud sends the local transcript, attachments included, to `/v1/threads/import` and then deletes the local copy, leaving it unchanged if the import fails. While a chat moves, the page starts no turn in it and changes neither its settings nor its messages, since those changes would stay with the copy the move deletes; deleting the chat, alone or with every chat, waits for the move to end. Pinning a local chat or moving it into a project moves it to the cloud first.

The Data tab and native backups handle chats in either place, as on main. Imports follow storage: with cloud sync the harness's `/v1/import` imports the uploaded export, while chats kept on this device are imported in the browser, which parses a ChatGPT or Claude `conversations*.json` export, or a Tinfoil export (in a worker), with main's parsers and stores each chat as a local chat. Claude project files always go to `/v1/import`, since projects need cloud sync. Export Chats, offered to every user, writes the previous client's `conversations.json`, or a ZIP adding `attachments/` and `manifest.json` when a chat has images: the chats on this device (in this tab when signed out) and, with cloud sync, each stored chat read through `/v1/threads/transcript`. A stored chat whose transcript is refused, while a reply streams or when an attachment is unreadable, or every stored chat when the session does not offer `transfer`, is read through `/v1/threads/get` instead, its attachments fetched one at a time from `/v1/attachments/get` and a missing one listed as a warning. Without premium, project chats are left out. Native backups, offered to a premium account with an encryption key, start from the harness's `/v1/export` archive of the cloud's projects and chats; the browser adds the chats on this device as `local_chats` entries with their images, relationships, omissions, and manifest counts and hashes, so the archive passes main's native backup validation. Restoring validates an archive in the browser and uploads only its cloud part, as a native backup of its own, to `/v1/import`, since the harness would turn local chats into cloud chats; the local chats are restored on this device under main's ids for the account and backup.

Closing the page detaches the stream; a local chat's run keeps saving when the view moves to another chat, and reopening the chat or reloading during the run rejoins it. Stop sends the active run id to the cancel endpoint. A request whose acceptance was not received retries with its original nonce, a dropped stream follows its run with the last event cursor, and a run that ended with an error runs again (a continuation continues again; any other turn regenerates the reply to the last user message). Queued turns run on the server, including priority sends and removal. Account changes abort outstanding requests and discard the previous view. A key change does so for requests that carry the content key and for an open stored chat; a local chat's run and keyless requests, such as read aloud, continue.

Message actions name messages by id: Regenerate names the reply (a user message without one is sent again as an edit), and Continue is a turn of kind `continue` that streams into the reply `RUN_STARTED` names. Stored chats delete and edit messages and fork through `/v1/threads/messages/*` and `/v1/threads/fork`; local chats change their own copy and fork on the device. A new stored chat's first turn leaves `presetId` out so the harness stamps the profile's `defaultPromptPresetId`; a local chat stamps it on its copy, and a saved prompt's `model` and `webSearchEnabled` apply to the chat when it is chosen. The session and each run report the quota (`rateLimit`), which the sidebar's usage card and the quota banner read; a finished run's spend counts until a later report includes it.

Features the paired harness added are offered only when `session.features` names them, so the client degrades against an older harness: `speech` (read aloud), `localShare` (local shares, and the share dialog's status and revocation), `fork`, `messageActions` (stored chats' message deletes and edits), `continue`, `defaultPromptPreset` (the default prompt; the custom default prompt stays otherwise), and `transfer` (moving chats between the cloud and this device, and reading a stored chat's transcript for an export).

The paired harness revision is required for first-turn project/preset selection, queue priority sends, bulk deletion, favicon lookup, normalized shares, and context usage. See the harness's `IMPLEMENTATION.md` for deployment prerequisites, model catalog reconciliation, token expiry, and replica affinity. This code change does not deploy either service.

Run the checks without starting a development server. The widget check needs the harness repository checked out next to this one:

```sh
npm run test:unit -- --run
npm run lint
node node_modules/typescript/bin/tsc --noEmit --incremental false
node ../confidential-tinfoil-harness/scripts/check-widgets.cjs .
```

The Go tests also check generated events against the browser reducer and validate legacy rows and native archives using frozen reference validators under the harness's `scripts/fixtures/legacy-webapp/`. Live attestation and browser smoke testing against the deployed service remain rollout checks.
