# Webapp harness integration

All chat routes use the existing chat UI and `src/services/harness/`. `/harness` is an alias for the main page. The harness origin defaults to `https://chat-api.tinfoil.sh`; set `NEXT_PUBLIC_HARNESS_ENCLAVE_URL` to use another deployed harness's HTTPS origin. `HarnessClient` uses the Tinfoil SDK to verify `tinfoilsh/confidential-tinfoil-harness` for JSON, multipart uploads, binary downloads, and SSE. There is no direct model or sync connection and no development attestation bypass.

The browser owns rendering, navigation, microphone recording, passkey ceremonies, anonymous credential acquisition, custody of the content encryption key, and the chats it keeps on the device. The harness owns prompts, model routing, tools, the turn queue, token budgeting, projects, memory, search, sharing, archive conversion, and the transcripts and settings of synced chats. Built-in prompt text comes from the session catalog for viewing and copying in the prompt library.

Anonymous clients call `GET /api/keys/chat` at `NEXT_PUBLIC_API_BASE_URL` directly, so controlplane sees the client IP. The issued `free_` key is cached only in memory and sent as the bearer credential through the harness's attested transport. Concurrent requests share issuance, expiry or HTTP 401 refreshes the key, and account changes abort pending issuance and clear the cache. The browser uses quota metadata for display; the harness validates the key through the existing `/api/shim/validate-key` endpoint before starting work, and downstream services continue enforcing quotas. No identity-forwarding secret or controlplane code change is needed. Signed-in clients continue sending their Clerk JWT.

Anonymous temporary state belongs to the issued key. Reconnects with the same key survive IP changes; a rotated daily key starts a separate scope. The deployed harness must run on a host accepted by controlplane's existing key-validation IP check. A local webapp can use that deployed harness.

The existing message renderers, widgets, sidebars, project panels, settings, and key recovery dialogs remain. Tool results and project/context usage are server data. Imports upload the original file; the progress control checks the returned job id. Image galleries download full-size images through the harness, naming the chat (`threadId`) so stored attachments resolve. A stored document's message carries no text, so opening the document or the share dialog reads it on demand through `/v1/attachments/get`, which returns the extracted text; a local chat reads it from the document's stored descriptor, and a shared chat through `/v1/attachments/get-public`. Read aloud, when the session offers `speech`, asks the harness's `/v1/speech` for each chunk of at most 600 characters (two at a time) and plays the 24 kHz PCM it streams back through the same attested client. Account management, billing, public map tokens, safeguard flags (`/api/users/me/safeguard-flags`, polled every 30 seconds while visible), and legacy opaque passkey credential lookup retain their controlplane requests. The harness gives the safeguards each chat's id as its conversation id, so a flag marks that chat read-only by id, for stored and local chats alike.

Storage follows the device's cloud sync setting, as on main. With cloud sync on, the harness stores chats and settings. Without it (the default for a new account), and for signed-out visitors, chats are local threads: the browser keeps them in the `tinfoil-chat` IndexedDB, or in session storage for the tab when signed out, and keeps settings under `tinfoil-user-prefs-local-profile` in local storage (imported once from the previous client's per-setting keys). Each local turn sends `local: true` with the thread's transcript and the settings a prompt reads, never the content key, and the browser merges the run's messages, per-reply metadata, and title back into its copy; image bytes travel only with the last few image messages. Chats the previous client stored there open through a port of the harness's `legacy.go`. With cloud sync on, Enable local chats adds a Local tab for such chats. Projects, favorites, server search, import, export, and native backups need cloud sync. A signed-in user shares a local chat from its transcript without image bytes (`local: true` on `/v1/threads/share`, when the session offers `localShare`); shares of either kind are keyed by the chat, so the share dialog reads their status and revokes them by chat id. Session storage also holds run routing hints and UI preferences; keys and passkey recovery state remain in local storage. Signout and account changes clear the chat database, local chats included.

Closing the page detaches the stream; a local chat's run keeps saving when the view moves to another chat, and reopening the chat or reloading during the run rejoins it. Stop sends the active run id to the cancel endpoint. A reconnect follows that run with its last event cursor; a request whose acceptance was not received retries with its original nonce. Queued turns run on the server, including priority sends and removal. Account and key changes abort outstanding requests and discard the previous view.

The paired harness revision is required for first-turn project/preset selection, queue priority sends, bulk deletion, favicon lookup, normalized shares, and context usage. See the harness's `IMPLEMENTATION.md` for deployment prerequisites, model catalog reconciliation, token expiry, and replica affinity. This code change does not deploy either service.

Run the checks without starting a development server:

```sh
npm run test:unit -- --run
npm run lint
node node_modules/typescript/bin/tsc --noEmit --incremental false
node ../confidential-tinfoil-harness/scripts/check-widgets.cjs .
```

The Go tests also check generated events against the browser reducer and validate legacy rows and native archives using frozen reference validators under the harness's `scripts/fixtures/legacy-webapp/`. Live attestation and browser smoke testing against the deployed service remain rollout checks.
